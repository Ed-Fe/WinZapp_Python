# Neonize bridge: route coverage

Compared with the routes WPPConnect Server defines for WinZapp (`client/api/dist/routes/index.js`). The bridge implements **210 of 220**; **6** are not implemented. A missing route makes the feature that needs it unavailable (or a harmless 404 in the log) when the Neonize engine is selected.

This list is generated by comparing route names, so a feature may be reachable by another route than the one named here (for example, the client sends voice notes with `send-voice-base64` and files and photos with `send-file`, which are implemented).

## Not implemented, by area

**Chats and messages**: `take-screenshot` (there is no browser page to capture)

**Business and catalog**: `create-collection`, `del-collection`, `edit-collection` (their stanzas are not known: WhatsApp Web only loads that code on a Business account, and no other client documents them)

**Profile and privacy**: `get-battery-level` (a linked device does not receive the phone's battery)

**Calls**: `call/upgrade-video` (the call layer has voice only)

## Implemented with limits

These answer, but not everything the WPPConnect route does. None of the routes added after the first 71 was run against a real account yet.

- `group-property`: only `announce`, `restrict` and `ephemeral`; other properties answer 400.
- `last-seen/:phone`, `chat-is-online/:phone`: answer from an in-memory presence cache fed by presence events; `unsupported` when there is no data or the person hides it.
- `set-profile-pic`: JPEG, and other images converted to JPEG with Pillow (415 for a non-image).
- `get-all-labels`, `delete-all-labels`: only labels created through the bridge (`labels.json`); the labels the account already had are in the app state mirror (below) but these routes do not read it yet.
- `message-ack`: answers from the receipts the bridge stored (they survive a restart); 404 when none. In groups, `deliveryRemaining` counts the members who sent no receipt yet.
- Group message ticks (`onack`, `get-messages`): delivered/read/played only when every recipient has delivered/read/played; a member who delivered but never read stops blocking the read tick after a 10-minute grace (a guess, not confirmed on a real group).
- `message-comments/:messageId`: reads and sends community announcement comments with the message secret that whatsmeow keeps in `session.db`. Receiving, decrypting and the send format are written from the whatsmeow source, not confirmed against real traffic; the server may not accept the sent stanza.
- `media-upload-progress`, `media-download-progress`: real progress only with the fork DLL that exports `UploadFile`/`TransferProgress`/`DownloadAnyToFile` (and only for `send-file` with an `uploadId`, and `get-media-by-message` with a `progressId`); stock neonize sends no progress events.
- `status` of a session after a ban, outdated client or replaced stream is `terminalFailure`, which the client's health loop does not restart.
- `all-new-messages`: cursor kept in memory per session; the first call returns `[]` and a restart resets it.
- `reply-button/:messageId`: answers `dynamic`, `list`, `template` and `native` (the `quick_reply` of an interactive message, sent as an `interactiveResponseMessage` with a `quick_reply` native flow response). The other native buttons (link, copy, call) are opened by the client and never reach the bridge. The `native` format is the one TeleZapp sends; it was not tried on a real account from here.
- `temporary-messages`: accepts 0, 24 hours, 7 days or 90 days.
- `meta-ai-terms`: always `UNKNOWN`; `meta-ai-terms/accept` answers 501 (accepting is not verified for this neonize build).
- `clear-chat`, `delete-chat` and the `*-all-chats` routes, `save-contact`, and the label routes send app-state patches written from the WhatsApp Web layout, not confirmed on a real account.

## Through WinZapp's neonize build (raw queries and app state mutations)

These need WinZapp's neonize build (`neonize_patches/neonize/0006`, `whatsmeow/0003`): raw info queries and MEX queries (`send_iq`, `send_mex`), an event for every app state mutation (`AppStateMutationEv`, kept in `app_state.db` by `app_state_mirror.py`) and REMOVE mutations. On an older build each answers 501 with the code it answered before. The stanzas were read from WhatsApp Web's own modules over CDP on 2026-10-26; none was run against a real account yet.

- `custom-lists` (`custom_lists.py`): labels of type CUSTOM in the `regular` collection. The first read downloads `regular` once (a full sync) to learn the lists the account already has; until then it answers 503. A Business account reads but does not edit (403), as the WPPConnect route.
- `community-subgroups/:communityId/:subgroupId/join`, `.../cancel-request`, `deactivate-community` (`community_membership.py`): `w:g2` queries `join_linked_group`, `cancel_membership_requests` (with the account's LID) and `delete_parent`. The join does not first read the group (WhatsApp Web asks whether it is hidden or suspended); the server's refusal answers instead.
- `privacy/status` (`status_privacy.py`): an app state mutation (`regular_high`, `status_privacy`, version 7), as WhatsApp Web; it sends no query to the server. The people of a list go as WhatsApp Web writes them (`<digits>@s.whatsapp.net`, a LID as is), not as the client sends them (`@c.us`). `privacy` still reads who sees my Status from the server (`get_status_privacy`), which may lag behind.
- `remove-contact` (`contact_removal.py`): a usync "delta" query telling the server the contact is gone (`contact_sync.py`), then a REMOVE of `["contact", "<digits>@s.whatsapp.net"]` in `critical_unblock_low`, only for a saved contact. `save-contact` now sends the "add" query the same way before its app state entry. Both queries are best effort: a refusal is logged and does not stop the save or the removal. The index form was checked in WhatsApp Web (`toString({legacy: true})` of a number is `@s.whatsapp.net`).
- `newsletter/:id` PUT and DELETE (`channel_admin.py`): MEX mutations 24250201037901610 (`xwa2_newsletter_update`) and 30062808666639665 (`xwa2_newsletter_delete_v2`).

## Commerce and interactive messages (WinZapp's neonize build)

Read over CDP from WhatsApp Web's own modules on 2026-10-26, with the business IQs Baileys keeps (`biz_iq.py`); none was run against a real account yet, and the seller's side needs a Business account.

- `commerce/account`, `commerce/catalog/:chatId`, `get-products`, `get-product-by-id`, `get-collections`, `get-business-profiles-products` (`business.py`): the `w:biz:catalog` and `w:biz` business_profile IQs. A business account is one whatsmeow keeps a business name for; a seller's catalog follows WhatsApp Web's rule (`hasCatalog`); the sellers are the chats whose contact has a verified business name.
- `commerce/cart/...` (`commerce_cart.py`): the cart lives in `carts.json` (on the device, as in WhatsApp Web). Submitting places the order through the catalog GraphQL endpoint (`catalog_graphql.py`: `graph.whatsapp.com/graphql/catalog` with the public token WhatsApp Web carries, no account credential) and sends an OrderMessage, as `WPP.cart.submit`.
- `commerce/order/...`, `commerce/order-details/...`, `get-order-by-messageId` (`commerce_orders.py`): the order is read through the same endpoint with the order message's id and token (kept for order messages received from now on); accept, decline and a new status send WhatsApp Web's native flow messages (`order_details`, `order_status`); the buyer's "Confirm order info" sends `payment_method` "confirm". The countries gate WhatsApp Web applies to that button is not checked.
- `add-product`, `edit-product`, `del-products`, the three picture routes, `set-product-visibility`, `edit-business-profile`, `set-cart-enabled` (`catalog_admin.py`): `product_catalog_add / _edit / _delete` and `business_profile` "delta" (cart_enabled under profile_options, from how WhatsApp Web reads the profile). A picture is uploaded unencrypted to `/product/image` (`media_upload.py`, `MediaConn` of neonize 0007). `price` is in currency units.
- `send-buttons`, `send-list-message`, `send-pix-key`, `send-order-message`, `send-link-catalog` (`interactive_send.py`): the protos WhatsApp Web builds (native flow InteractiveMessage, ListMessage), with the `<biz>` node whatsmeow 0004 adds. wa-js also re-sends buttons to the recipient's phones in an older form; the bridge does not, so a phone may not show them.

## Upkeep

- `unhealthy` answers 503 but does not end the bridge (the reference server exits; here one process holds every account, and any page can reach it).
- `collect-page-garbage` collects the bridge's own garbage and answers its memory (`before`, `after`, `tookMs`).
- `backup-sessions`, `restore-sessions` (`session_backup.py`): a zip of each account's files, SQLite copied with its backup API; a restore never writes over a running account. Both need the bridge's secret, as `clear-session-data`, which logs the account out and deletes it like `delete-session`.
- `profile/:phone` answers what `check-number-status` does; `chatwoot` sends a Chatwoot conversation's outgoing text and attachments; `call/diagnostics` describes the call layer.

## Registered but answering 501

neonize/whatsmeow cannot do these, so the bridge says so instead of pretending: `call/group/offer`, `call/upgrade-video` (the call layer has no group or video calls; `call/offer` with `isVideo` too, and every call route but `call/reject` on a neonize build without the call layer); `get-battery-level`; `take-screenshot`; `create-collection`, `edit-collection`, `del-collection`. They count as not implemented above.
