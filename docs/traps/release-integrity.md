# Release integrity — what stops a forged update

> Immutable releases, signed manifests, environment secrets, SHA-pinned actions.
>
> Moved verbatim out of `CLAUDE.md` so it is read when the area is touched, not on every session. Keep it here: this is measured history, not a summary.

## Release integrity — what stops a forged update (`client/core/release_signature.py`)

**The threat is not a stranger on the network, it is anyone who can edit a release.** The updater hands a downloaded ZIP elevated write access to the install directory of hundreds of machines. `SHA256SUMS.txt` alone never protected against that: it is uploaded next to the ZIP it describes, so the eight accounts with write access — and anyone who steals one — replace both together. Four layers, each covering what the one before cannot:

- **Immutable releases** (a repository setting). Once published, a release's assets and tag are frozen, so nobody can swap `WinZapp.zip` on a release users already trust. This forces **draft → upload → publish** everywhere, and a draft does not fire `release: created` — which is why the stable pipeline is no longer started from the Releases page: **pushing a stable tag** (admin-only under the tag ruleset) runs `release.yml`, which tests, builds and leaves a **draft**. `.github/scripts/release_signing.py sign-stable <tag> --key <file>` then signs it and publishes; publishing triggers nothing else and never changes `main`. GitHub runs a tag's workflow *from the tagged commit*, so a release branch cut before this change runs the old pipeline — merge `main` into it first.
- **Signatures.** `release_signing.py` signs the exact bytes of `SHA256SUMS.txt`, whose first line (`# winzapp-version: <v>`, written by `build-windows.yml`) binds it to one version — without that line a genuine signature on an *old* release could be replayed under a newer tag. `check_release_manifest()` refuses a version mismatch, a missing manifest, a missing `.sig` and an unknown key. **Stable keys live offline** (a primary and a backup, passphrase-encrypted, never on GitHub), so a stolen GitHub account cannot ship a stable update. **Alphas are signed in CI** by `ALPHA_SIGNING_KEY` so they keep publishing on every push to `main`; that key is weaker by construction (anything that reaches `main` can make CI sign it), so it is accepted **only** for a release that is alpha by both its tag and its signed version string — an opted-out user is never exposed to it. `client/core/release_keys.py` holds the public keys; **both empty means signing is not set up yet** and every path behaves as before (the updater skips the check, `ci-sign` signs nothing and exits 0). Once keys are committed, enforcement is on for every build made after, and `ci-sign` fails an alpha run whose secret is missing rather than publish something those builds refuse. Order when setting up: secret first, then commit `release_keys.py`. Never edit a key out of `release_keys.py` casually — installed clients only learn a new key through a release the old one signed.
- **Secrets in environments, not the repository.** A repository secret is readable by a workflow pushed to *any* branch by anyone with write access. `ALPHA_SIGNING_KEY` is read from the `alpha-release` environment (the old `RELEASE_BUMP_TOKEN` secret is no longer used and can be deleted from the `release` environment); the restriction itself (stable tags / `main` only) is configured in Settings > Environments. Never put required reviewers on `alpha-release` — that silently stops every alpha.
- **Actions pinned to commit SHAs**, kept current by `.github/dependabot.yml`. A tag can be repointed at different code after the fact, and several of these steps run with `contents: write` or a release token.

## The Neonize bridge is part of the shipped bytes (`winzapp_tools/bridge_build.py`)

Every onedir build freezes `neonize_bridge/` into `neonize_bridge/neonize_bridge.exe`, and with it **the Go DLL of WinZapp's neonize build** that holds users' WhatsApp keys: official neonize at the release approved in `neonize_bridge/neonize_upstream.json` plus `neonize_bridge/neonize_patches/` (neonize, whatsmeow, meowcaller), compiled by `neonize_bridge/build_neonize.py` (`docs/reference/neonize-build.md`). What stops it from drifting:

- Everything that goes into the DLL is in this repository or pinned: neonize and meowcaller by full commit, whatsmeow by module version (checked against the Go checksum database), protoc by SHA-256. The **build identity** (`neonize_upstream.checkout_identity`: the pins and every patch byte) is written into `neonize_bridge/.venv/.neonize-build-sha256` by `build_neonize.py install` and by `prepare.py`; `bridge_build.build()` runs `prepare.py` again whenever that marker is missing or differs, so a stale, hand-edited or unexported build is never frozen (a workspace with work not exported builds with no identity at all).
- `prepare.py` downloads a published build only when the manifest's `release` carries this checkout's identity, from GitHub hosts, checking its **SHA-256** and what is inside the archive (allowed file types, no `.pth`/`sitecustomize.py`, size limits); otherwise it compiles from source, which is what the release workflow does (Go + the MSYS2 gcc in `build-windows.yml`).
- Every other package of the bridge is installed from `neonize_bridge/requirements.lock` with `--require-hashes`, and PyInstaller from `requirements-build.lock` (the same versions as the client build, checked by `tests/test_bridge_build.py`). Changing `requirements.txt` means regenerating the lock: `uv pip compile neonize_bridge/requirements.txt --generate-hashes --python-version 3.13 --python-platform windows -o neonize_bridge/requirements.lock`.
- `build-windows.yml` fails the release when the zip has no `neonize_bridge/neonize_bridge.exe` or no neonize DLL inside it (`_internal/neonize/neonize-windows-amd64.dll`). The bridge needs no `ffprobe`: it measures voice notes and video itself (`neonize_bridge/media_probe.py`).
- A release build depends on GitHub (neonize, meowcaller, protoc) and the Go module proxy staying reachable; if one is not, the build fails closed.
